# Observable workflow friction and evidence limitations

This analysis distinguishes **visible exceptions or information gaps** from **potential stakeholder pain pending validation**. It does not estimate engineering hours, cost, frustration, or the frequency of any issue across Python projects. The Milestone 1A sample is a narrow, all-Dependabot frame, with Sample A (20 PRs) and purposive Sample B (7 PRs) kept separate.

| Category | Observable evidence | Interpretation and boundary | Stakeholder question |
| --- | --- | --- | --- |
| Evidence distributed across artifacts | PR diffs, copied upstream body text, and review/status comments carry distinct facts; [baseplate.py#1054](https://github.com/reddit/baseplate.py/pull/1054) required the review thread to explain a local mypy type issue. PULSE separately collects multiple source categories. | **Source fragmentation is observable**; burden of correlating them for a person is not measured. CI/check histories were not systematically audited in the PR sample. | Which sources actually change an investigation decision? |
| Upstream/downstream relevance ambiguity | Phase 2's two candidate firings came from one bot PR with copied upstream notes and were both rejected. Copied notes appeared in 13/20 base and 6/7 discussion PRs. | **Observed classifier false-positive mechanism**, not proof of downstream friction or a maintainer's confusion. | Who reviews these signals, and how are irrelevant ones filtered now? |
| Historical-state ambiguity | Phase 2 parsed exact-ref target-package declarations in 2/8 frozen repositories; only one had a pre-release paired-path anchor. An older unchanged path can fall outside the in-window history method. | **Observed PULSE acquisition gap**; 2/8 is evidence coverage, never adoption. Public PR old/new versions do not reconstruct earlier release-boundary state. | When is point-in-time state needed, and what source establishes it? |
| Version/adoption ambiguity | Current or permissive declarations do not establish the installed target version or ordinary runtime/CI resolution in Phase 2. | **Observed PULSE inference boundary**; UNKNOWN must not become NO or zero adoption. | Is a declaration enough, or is resolved/installed version evidence required? |
| Exception processing | One [mypy PR](https://github.com/reddit/baseplate.py/pull/1054) showed reported test failure and code change; one [Uvicorn PR](https://github.com/Kludex/uvicorn/pull/2549) retained a version. Eight base PRs were explicitly superseded; three discussion PRs had rebase commands and up-to-date replies. | **Visible workflow variants**; not measured overhead, failure prevalence, or wasted work. Superseded bot PRs may be routine. | Which exceptions require investigation or escalation? |
| Completion ambiguity | The public PR record ends at merge/closure; Phase 2 did not collect downstream releases or establish a recovery-eligible denominator. | **Different evidence meanings:** PR disposition, dependency installation, migration completion, and production recovery cannot be equated. | What completion state does the stakeholder decide, and how is it verified? |
| Portfolio and ownership ambiguity | Neither Phase 2 research cases nor sampled public PRs show who selects and prioritizes an organization's repositories. | **Hypothesized process gap**, not observed user pain. | Is there a cross-repository decision at all, and who owns it? |

Only the first six rows contain directly observed source or PULSE-system limitations. Whether they are consequential in a real stakeholder's workflow remains open. The final row is an explicit hypothesis for [primary research](milestone-2-primary-research-questions.md).
