# Provisional PULSE requirements baseline

**Baseline status: provisional pending primary-research reconciliation.** No respondent has approved these requirements. This specification turns the [Phase 2 PIVOT](../phase-2/phase-2-findings.md), [Milestone 2 gaps](gap-analysis.md), and [Milestone 3 provisional workflow](to-be-process.md) into testable statements. It does not authorize implementation. The [primary-user hypothesis](primary-user-hypothesis.md) and [needs N-01–08](stakeholder-needs-hypotheses.md) remain unvalidated. The [public PR evidence](secondary-research/github-workflow-analysis.md) is an all-Dependabot sample, not the general upgrade workflow.

**Source strength:** A = direct Phase 0–2 system evidence; B = analytical-integrity rule; C = secondary public workflow observation; D = proposed design/stakeholder hypothesis; E = genuine stakeholder evidence (**none yet**). A source may have multiple levels; a technical observation never by itself validates demand. **Status:** `validated-existing` means observed in frozen Phase 2 cases, not production ready; `partially-existing` means current method has a material gap; `proposed-system-evidence-supported` is derived from a demonstrated gap; `provisional-secondary-evidence` uses the bounded PR sample; `provisional-stakeholder-dependent` needs genuine users. No row is `stakeholder-validated`. MoSCoW reflects [capability priorities](capability-prioritization.md), not a value score. `—` means no dependency/assumption recorded beyond the stated case boundary. Acceptance IDs resolve in [acceptance criteria](acceptance-criteria.md); future validation is planned, never performed.

The status vocabulary also reserves `deferred` for a justified later candidate and `out-of-scope` for a boundary exclusion; neither is an active baseline requirement. Status describes implementation/evidence maturity, **not** stakeholder approval. The [backlog](requirements-backlog.md) separately distinguishes current Phase 2 behavior from proposed, Not Implemented behavior.

## Reconciliation and change control

At a future Milestone 2A, genuine Google Form/interview evidence may **confirm, modify, reprioritize, split, remove, add, or leave unresolved** stakeholder-dependent requirements. In particular, BR-001/004, SR-001/003/005/006, FR-011/012, and the presentation/review assumptions need direct decision-owner testing. Changes must retain source, rationale, owner of the change decision, affected IDs, and revised AC/RTM rows in [change history](requirements-change-history.md). A preference for weaker evidence cannot silently override Level B integrity rules; any proposed tradeoff must be explicit and reviewed against the underlying evidence. No Level E or stakeholder approval is recorded in this baseline.
