# Public dependency-upgrade PR workflow analysis

This analysis uses the **frozen 20-PR base sample** and a separate **7-PR purposive discussion sample**. Counts below retain those denominators; they are not rates for Python projects or dependency upgrades. The [candidate-frame summary](github-pr-candidate-frame-summary.md) describes the title, first-page, date, repository, and bot bias. Detailed coded observations and source URLs are in [the JSONL dataset](github-pr-observations.jsonl). This is secondary observational evidence, not stakeholder validation.

## What entered the visible workflow

All 20 base and all 7 discussion PRs were Dependabot proposals. The search design favored `bump` titles, so it did not capture a useful comparison with manual or Renovate upgrades. The PRs visibly changed Python dependency files; four base PRs proposed grouped multi-package updates, such as [artichoke/nightly#284](https://github.com/artichoke/nightly/pull/284) and [Kludex/uvicorn#2549](https://github.com/Kludex/uvicorn/pull/2549). No sampled PR explicitly established whether its bot trigger was scheduled, security-driven, or initiated for another reason. Do not infer a trigger from the bot author alone.

## Initial evidence and provenance

Every selected PR exposed a dependency-file diff. In Sample A, 14/20 changed a manifest or requirements file and 6/20 changed a lockfile; in Sample B, the corresponding counts were 6/7 and 1/7. Bot bodies attached release-note sections in 10/20 base PRs and 5/7 discussion PRs, changelog sections in 9/20 and 1/7, and a compatibility-score **badge/link** in 16/20 and 7/7. The badge's underlying score was not independently verified. Copied upstream release notes/changelogs occurred in 13/20 base and 6/7 discussion PR bodies; each of these contained upstream issue links inside the copied text. Those links describe upstream package work, not observed breakage in the downstream repository. For example, [the mypy PR body](https://github.com/reddit/baseplate.py/pull/1054) contains copied mypy changelog text, while its downstream typing problem is documented separately in [a repository review comment](https://github.com/reddit/baseplate.py/pull/1054#discussion_r1904554245).

## Human review and validation

Visible human comments or reviews appeared in **6/20 base PRs** and **7/7 purposively selected discussion PRs**. Four base and four discussion PRs had a visible approval. A visible approval is a decision signal, not proof of all tests passing or a measure of labor. The connector record did not include a systematic audit of check-run histories, so this study cannot count successful CI validation. In [baseplate.py#1054](https://github.com/reddit/baseplate.py/pull/1054#pullrequestreview-2532549557), a reviewer reported test failures; the PR then included a library-code change and an explanation of the new mypy behavior before approval. In [uvicorn#2549](https://github.com/Kludex/uvicorn/pull/2549), a maintainer's [inline suggestion](https://github.com/Kludex/uvicorn/pull/2549#discussion_r1900374580) retained `websockets==13.1` even though the bot body proposed 14.1. The final diff did not upgrade `websockets`; the public record does not establish a broader compatibility incident.

## Exceptions and disposition

Sample A contained **9 merges and 11 closures without merge**. Eight of the latter carried an explicit Dependabot “superseded by” comment, for example [baseplate.py#1045](https://github.com/reddit/baseplate.py/pull/1045#issuecomment-2573463429) and [glimpser#2232](https://github.com/KristopherKubicki/glimpser/pull/2232#issuecomment-3071244680). Another bot comment said a grouped update was [updatable in another way](https://github.com/CODEX-CELIDA/execution-engine/pull/305#issuecomment-3070926423); one [ignored-release response](https://github.com/team-ocean/veros/pull/787#issuecomment-3718100919) was visible without the initiating human command. These show PR lifecycle exceptions, not necessarily failures or wasted work.

Sample B contained **4 merges and 3 closures without merge**. The three [Couchers backend PRs](https://github.com/Couchers-org/couchers/pull/5417) show human approvals with `@dependabot merge`; they supply decision signals but little substantive reasoning. Three Delphix pytest PRs, including [#598](https://github.com/delphix/virtualization-sdk/pull/598#issuecomment-4136405732), show `@dependabot rebase` followed by a bot response that the dependency was already up to date and the PR was no longer needed. The record does not show that a rebase itself completed. The remaining discussion case, baseplate.py#1054, shows the specific test/type-check issue and code change described above.

`pr_resolution_duration_hours` in the dataset measures creation to merge/closure. It is not engineering time, time saved, or evidence of a cause for delay; [statys#39](https://github.com/gugarosa/statys/pull/39) illustrates why a long interval alone cannot explain what happened.

## What this can and cannot say about tools

PR bodies bundled versions, upstream text, and sometimes status bots, while some decisions were in review comments or closure replies. This supports a **source-correlation question** for stakeholder discovery: which of those sources must a real decision-maker inspect? It does not prove that existing tools are inadequate, that reviewers feel burdened, or that PULSE would save time. The systematic check history, private discussion, cross-repository triage, and installed-version evidence were not observed. The [observed workflow](observed-workflow.md) is therefore an input to future stakeholder research, not the final As-Is process.
