# Milestone 3 — Predeclared validation cohort selection

## Selection protocol (recorded before release and repository lookup)

Scope is Python/PyPI only. The package seed pool is `click`, `pytest`, and `urllib3`: widely used general-purpose runtime or developer dependencies, chosen without checking release-specific downstream outcomes. For each package, query its public PyPI JSON metadata and find the newest stable release with a major-version boundary `N.0.0`, `N >= 2`, whose first file upload was in 2023-01-01 through 2024-12-31 UTC. Require a public GitHub upstream listed in package metadata, a completed 120-day post-release window by selection time, and a plausible direct-dependency ecosystem. Select the two qualifying package releases with the latest upload timestamps. Resolve ties by canonical package name. Previously studied NumPy 2.0, Pydantic 2.0, SQLAlchemy 2.0.0, and HTTPX 0.28.0 cannot be primary selections. Record all seed-pool exclusions. This target procedure uses package metadata and version boundaries, never failure reports or downstream issue/PR search.

Here “stable” excludes prerelease, development, postrelease, and local version identifiers. Later PyPI yank state is not an eligibility filter: using it could select on a post-release outcome. During a failed first execution, a diagnostic metadata check exposed the yank flag of one candidate distribution. That flag was not used to select or exclude any target, repository, or cohort member; the implementation was corrected to match the predeclared rule before candidate search.

Use each selected release's first PyPI distribution upload timestamp in UTC as the release anchor. The case window is the 30 calendar days before the UTC release date through the 120 calendar days after that date, inclusive. Do not alter windows after viewing outcomes.

For each selected package, use authenticated GitHub **code search** as a dependency-source candidate generator. Make exactly two queries, `<package> in:file filename:pyproject.toml` and `<package> in:file filename:requirements.txt`, each with `per_page=30&page=1`. Preserve returned order, query, retrieval time, and every distinct repository in a machine-readable ledger. This is an API-indexed convenience frame, not a complete dependent population. If the API is unavailable, stop selection and report the limitation rather than substituting a hand-picked list. Evaluate the union of these two result pages; do not add familiar repositories manually.

For each candidate, inspect only repository metadata, the matching current default-branch manifest, and general commit activity counts within the declared case window. Do not inspect commit messages or diffs. Only root `pyproject.toml` or root `requirements.txt` search hits qualify; nested hits remain in the exclusion ledger. A candidate qualifies if it is public, not archived now, not a fork, not the upstream or owned by the upstream organization, has GitHub primary language `Python`, directly declares the canonical target package in a supported root manifest, has at least two public commits in the window, and its GitHub repository size is at most 500,000 KB. The matching dependency declaration may be a base or optional group; retain that distinction. A current declaration establishes cohort membership at selection time, not adoption at release time. Exclude candidates with missing, malformed, unsupported, or indirect-only declarations. Retain one ledger row per evaluated repository and every exclusion reason. A present-day archive flag is a conservative proxy; it does not reconstruct historical archive status.

Rank eligible repositories by ascending SHA-256 hex digest of `<case-id>/<lowercase-owner/repository>`. Select the first six eligible repositories. Record the full eligible population, ranks, and hashes so selection is reproducible. A cohort below five qualifies only for a **PARTIAL** milestone classification; do not fill it manually. Keep all frozen members in future denominators even if collection or historical pairing later fails. Record project type for descriptive diversity, but never override the hash ranking to improve it.

Before the cohorts are frozen, allowed inspection is limited to identity, public metadata, archive/fork/size status, default-branch dependency manifests, direct declarations, and general commit counts/dates. Prohibited inspection includes release-specific issues, PRs, failure discussions, migration commits/diffs, detector output, remediation, recovery, and known release outcomes. Any accidental exposure must be logged and cannot be used for inclusion. Freeze the case YAML and candidate/exclusion ledger before later forensic collection. These convenience cohorts are bounded validation sets, not representative samples or ecosystem incidence estimates.

## Results

The protocol was committed before release lookup (`fc3ec53`, clarified in `7f3c495`), and the selection implementation and logged PyPI metadata exposure were committed before candidate search (`5ce6442`). The generated [candidate and exclusion ledger](cohort-selection-ledger.json) and the two case definitions were frozen at `429d36e`, before any release-specific issue, PR, migration, remediation, detector, or historical-transition collection. The ledger contains both query result pages in API order, every evaluated repository, direct-dependency evidence, activity dates, exclusion reasons, eligible hash order, and the selected flag. Its selection timestamp is 2026-09-27 03:24 UTC.

The three-package seed pool produced `pytest 8.0.0` (first PyPI file uploaded 2024-01-27 21:47:54 UTC) and `urllib3 2.0.0` (2023-04-26 17:21:22 UTC). `click` had no qualifying major boundary in 2023–2024; its 8.0.0 boundary was earlier. Both selected packages have public GitHub upstreams in PyPI metadata. These are metadata-based target selections, not choices based on known compatibility incidents. See the recorded [PyPI project metadata](https://docs.pypi.org/api/json/) and the exact package JSON URLs in the ledger.

The 30-before/120-after policy yields 2023-12-28 through 2024-05-26 for pytest and 2023-03-27 through 2023-08-24 for urllib3. Both windows are inclusive UTC calendar dates. Case configurations are [pytest 8.0.0](../../cases/pytest-8.0.0.yaml) and [urllib3 2.0.0](../../cases/urllib3-2.0.0.yaml). The current-root manifest restriction and first-page code-search frame are explicit; the [GitHub code-search API](https://docs.github.com/en/rest/search/search#search-code) result order was captured rather than treated as a permanent global ordering.

### Interpretation and gate

Current default-branch manifests were used only to verify positive dependency-based membership. Some current constraints mention versions released after the case window; they must **not** be interpreted as adoption, exclusion, or compatibility at release time. Historical dependency state remains to be collected later, and every frozen member stays in the denominator even if it becomes unavailable or has unresolvable packaging history. General activity was checked by requesting at most two commit records per candidate and retaining dates only; commit messages and diffs were not inspected. No accidental release-specific issue, PR, or remediation evidence was encountered. The PyPI yank flag exposure noted above was not used.

Milestone 3 is **PARTIAL**. Two new releases and rule-based frozen cohorts exist with auditable direct-dependency evidence and a complete exclusion ledger, but the bounded first-page/root-manifest frame produced only two pytest repositories. The search frame is neither a random ecosystem sample nor stable across future index updates. The frozen ledger makes this execution reproducible; rerunning live search later may produce a different frame. No ecosystem-wide adoption or compatibility rate can be inferred from these cohorts.
