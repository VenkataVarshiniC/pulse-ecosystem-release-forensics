# Milestone 4 — Detector evaluation preregistration

This protocol is frozen **before** candidate generation on the Milestone 3 cases. It applies to the unchanged `pytest-8.0.0` cohort of two repositories and `urllib3-2.0.0` cohort of six. The cases and cohort-selection ledger are fixed at commit `e25de6e`. Selection membership means a direct dependency declaration on the default branch at selection time; it is not evidence that the target was installed or declared during the historical window.

## Evidence acquisition and evaluation order

Run the existing PULSE collector for both cases into separate new external roots and preserve every task outcome, raw collector envelope, and attempt journal. Use bounded authenticated GitHub pagination with no hand-supplied issue/PR URLs. Run the existing path-scoped historical reconstruction for all eight repositories, without manual SHAs. Preserve its exact-ref states and unresolved paths. Record operational completeness separately from current-file availability and analytical sufficiency. Do not remove any cohort member after a failure. Primary evidence must have `capture_method=collector`.

Only after collection, run the **unchanged** existing candidate detectors on the collected raw snapshots and defensible historical dependency transitions. Preserve the first-pass candidates as an immutable machine-readable baseline with candidate ID, rule, stage, repository, source artifact type and URL, and firing reason. A repeated record with the same candidate ID is counted once; different rule IDs on one source are separately reviewed candidates. Do not silently deduplicate distinct stages or rule firings. Do not add manual examples to the detector population. Evaluate only candidates from the frozen cohort and declared window; note any collector limitations.

Analyst review is separate from PULSE generation. Inspect the preserved source body or other available source content, not merely its title or the detector's reason. Every unique emitted candidate receives exactly one `accepted`, `rejected`, or `needs_review` decision, a structured reason code, a written explanation, and a review timestamp. These are **analyst reviews of PULSE-emitted candidates**, not automatic system truth. Supplementary external lookup is allowed only when needed to adjudicate a surfaced candidate and must be labeled; no web search for examples from zero-candidate repositories. If the preserved evidence cannot support a decision, use `needs_review`.

## Acceptance boundary from Phase 0/1 lifecycle definitions

- **Adoption readiness:** a downstream compatibility declaration, merged compatibility change, or passing target-version test. This is not ordinary observed adoption.
- **Observed adoption:** a manifest or lockfile selects the target version, or ordinary downstream CI/runtime resolves it. A permissive range or a changed range that merely accepts the target is insufficient by itself. The existing `dependency.target_accepted` rule is reviewed under this stricter definition.
- **Migration friction:** the source demonstrates a version-specific failure, incompatibility, deprecation break, or concrete migration task in a stated environment or code surface. A package/version mention, term match, or timing alone fails.
- **Remediation:** the artifact itself documents a pin, workaround, revert, code/test change, or downstream release intended to address release-associated friction. A reference to someone else's fix is not an action by this artifact. A constraint narrowing without evidence of intent does not establish remediation.
- **Recovery signal:** an explicit qualifying event for a named cohort repository within the case window, such as a downstream support release or a previously failing ordinary CI path passing. Issue closure, upstream patching, elapsed time, and silence do not qualify.

The categories are forensic evidence types, not a required chronological or causal chain. Review assesses the claimed stage on its own evidence. A candidate with a real event assigned to the wrong stage is rejected for that candidate stage; it is not relabeled after baseline generation. Pre-release events may be relevant if within the declared window. The source must identify the target package and version in context or otherwise provide direct version-linked evidence. Review does not infer motivation from temporal proximity.

## Decision and reason taxonomy

Use one primary reason code per candidate, with written context. Accepted codes: `direct_stage_evidence`. Rejected codes: `target_version_not_implicated`, `generic_dependency_mention`, `temporal_coincidence_only`, `mentions_other_remediation`, `bot_or_dependency_update_noise`, `unrelated_failure`, `wrong_lifecycle_stage`, `duplicate_evidence`, `outside_window`, `historical_dependency_not_established`, or `other_documented_reason`. Unresolved codes: `insufficient_source_context`, `historical_dependency_unknown`, or `source_unavailable`. The historical codes are contextual, not automatic vetoes: a concrete target-version failure can be accepted even when manifest history is unavailable. If a genuinely new recurrent reason is needed, document it as an emergent taxonomy addition without changing earlier decisions silently.

For contextual historical status, use `historically_supported` when at least one exact-ref file state in the declared window contains a parsed target declaration; this does **not** prove target-version installation. Use `historically_not_established` only when all configured paths have complete, parsed before/after states and none declares the target. Use `historically_unknown` otherwise, including missing anchors, unavailable files, ambiguous declarations, or collection failure. Record path-level statuses separately. Neither contextual status nor current cohort membership silently determines candidate acceptance.

## Metrics and decision on tuning

For each case, repository, stage, and rule report emitted, accepted, rejected, and `needs_review` counts. `reviewed = accepted + rejected`. **Reviewed-candidate precision** is `accepted / (accepted + rejected)`, always shown with numerator and denominator. When the denominator is zero, precision is unavailable, never zero. Unresolved candidates are excluded from that denominator and reported separately. Review burden is both emitted candidates per frozen repository and reviewed candidates per frozen repository, including zero-candidate members. Do not estimate time saved.

The metric concerns only emitted candidates. There is no independent gold universe of true events, so **recall is not measured**. Zero candidates means only that the current rules emitted none from collected evidence. These convenience cohorts do not support ecosystem prevalence, adoption, or compatibility-incidence estimates.

First calculate and preserve all baseline counts and decisions. Consider a detector change only after identifying a repeated general false-positive mechanism across at least two distinct source artifacts; prefer a mechanism spanning repositories. Any change must apply generally, preserve the baseline, have regression tests, and be rerun against the same raw evidence with before/after metrics. Do not add repository-, issue-, or SHA-specific exceptions. If the evidence does not support a general rule change, make no change and report the false-positive pattern. The final milestone gate is PASS only with evaluable candidates in both cases, complete review outcomes, characterized false positives, and transparent collection limits; otherwise use PARTIAL or FAIL according to the stated milestone gate.
