# M5.2 backend capability contract — specification only

No FastAPI route, HTTP URL, request model or database migration is created here. The planned application layer is **React + TypeScript → FastAPI/Python → PostgreSQL → existing PULSE evidence and analysis**. Prefer a small set of case/snapshot-scoped capabilities over a broad generic query API. Reads join operational `core` and `ingestion` records by selected identities; governed `analytics` marts may supply read-only summaries. The backend must enforce scope and provenance, not accept a client-provided arbitrary SQL, artifact path, or unvalidated snapshot state. Power BI has a separate analytical-consumption contract.

| Capability | Read/write; source | Minimum result / validation |
|---|---|---|
| List investigations | Read; `core.investigation_case`, `core.dependency_release`, `core.analysis_snapshot`, cohort membership | Case/release/window, declared member count, exact available snapshot ID/state; normal mode lists approved `PUBLISHED_VALIDATION`, no implicit latest DRAFT. |
| Get investigation and cohort | Read; case, release, membership and selected snapshot; optional `analytics.bridge_case_repository`/`fct_repository_investigation` summary | One case version and snapshot; 2/6 frozen members retained; source/rule/model context, literal missingness. |
| Get repository investigation | Read; member, selected task/observation/assessment/finding/candidate relations | Verify member belongs to case and snapshot; distinguish collection, historical state, candidate count and findings. |
| List evidence and historical observations | Read; `core.evidence_artifact`, `core.dependency_observation`, `core.historical_pair`, selected artifact/run/task; source registry | Typed observation, exact ref/path, before/after/AFTER_ONLY status, event vs retrieval clock, capture method; stable sort and bounded pagination. No raw credential exposure. |
| Get artifact/provenance detail | Read; evidence artifact, external reference, ingestion source/task/run/attempt, selected links | Original locator, digest, method, source, timestamp/ref, candidate/finding links when recorded; enforce selected snapshot and authorize locator before serving. |
| List/get findings | Read; selected `core.lifecycle_finding`, `core.sufficiency_assessment`, source reasons and actual support edges | Literal UNKNOWN/NO/QUALIFYING_EVIDENCE with reason, sufficiency, rule version, provenance. Empty support edge is explicit, not fabricated. |
| List/get candidates and reviews | Read; selected candidate/review plus replay lineage | Candidate ID, artifact, rule/origin, chosen decision/reason, inherited vs direct provenance and original-review link. Published replay decisions are read-only. |
| Submit candidate review | **Conditional write**; `core.analyst_review` and selected DRAFT review linkage only | ACCEPT/REJECT/NEEDS_EVIDENCE with nonempty reason, verified candidate/artifact/case/snapshot, authenticated or otherwise governed human reviewer identity, server timestamp, expected review version and idempotency key. Reject PUBLISHED_VALIDATION, stale/duplicate terminal, identity mismatch, absent authority; commit atomically. No auto-reanalysis or published mutation. |

The read response envelope should carry `case_version_id`, `analysis_snapshot_id`, snapshot state, rule/model version, source/capture method where applicable, stable entity IDs for navigation, and explicit `status`, `reason`, and missing/unavailable fields rather than collapsing all nulls. Client-visible errors should distinguish `NOT_FOUND_IN_SELECTED_COHORT`, `SOURCE_UNAVAILABLE`, `PROVENANCE_MISMATCH`, `STALE_REVIEW`, `PUBLISHED_IMMUTABLE`, `INVALID_DECISION_REASON`, and `REVIEWER_NOT_AUTHORIZED`; network failure is a separate frontend state. Do not infer “no evidence” from an API failure. Scope all pagination and filters to one case/snapshot, use stable ordering, and prevent cross-snapshot identity mixing. Keep credentials and internal storage paths out of responses.

**Write safety gate:** V005 guards updates/deletes to published selected candidates/reviews/findings and new links into published snapshots. The two current replay candidates are immutable inherited REJECT examples, not a writable review queue. M5.2 can implement and test all read capabilities immediately. A review-submission implementation requires an eligible new DRAFT candidate/snapshot plus a minimal trusted reviewer-identity policy; neither a current published candidate nor an old historical DRAFT snapshot should be repurposed as a test target. Use isolated fixtures to test the conditional write contract, then create a separately governed later analytical version after review. Never insert an apparently new human review on a published candidate to evade the snapshot guard. A non-eligible target returns `PUBLISHED_IMMUTABLE` or equivalent and leaves all rows unchanged.

The backend does not create evidence, decide business priority, edit frozen raw captures, publish analytical snapshots, or certify recovery. Authenticated nonpublic collection, retention, performance targets and multi-user administration remain outside this milestone pending policy and stakeholders.
