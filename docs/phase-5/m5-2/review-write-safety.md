# Human review write boundary

**Production submission is disabled.** The default `ReviewPolicy` has no trusted reviewer identity and no eligible DRAFT snapshot IDs. `PULSE_API_ENV=local` also fails the write gate. The two current published candidates return `PUBLISHED_IMMUTABLE` before a write connection opens; no fake new reviewer action is inserted. Existing inherited REJECT rows remain provenance records tied to original reviews, not clicks in this application.

The POST contract accepts typed `ACCEPT`, `REJECT` or `NEEDS_EVIDENCE`, nonblank reason, optional note, `expected_review_id` and an 8–128 character `idempotency_key`. Reviewer identity comes from a server-controlled policy, never the request body. To enter the actual write transaction all conditions must hold: `PULSE_API_ENV=test`, database `pulse_test`, an explicit test-fixture snapshot allowlist, trusted fixture reviewer identity, selected candidate matching case/member/snapshot, selected artifact in that snapshot, snapshot state `DRAFT`, allowed decision, nonblank reason, and expected current review ID. This **does not** create a production authority model; G8 and the legitimate new DRAFT workflow remain open.

The writer locks the selected candidate row, checks the current selected review, then inserts one `core.analyst_review` and one `core.snapshot_review` link inside a PostgreSQL transaction. A stale expected ID or existing terminal review returns `STALE_REVIEW`. The database's existing terminal unique index provides a second guard. For idempotency, `review_id` is a deterministic UUID derived from snapshot, candidate and client key. A retry with the same decision/reason/note/server reviewer returns the same receipt with `idempotent_replay=true`; reuse with changed content returns `IDEMPOTENCY_CONFLICT`. `NEEDS_EVIDENCE` can precede a later terminal decision in the same review cycle; the sequence advances. No finding changes automatically, and a later conclusion would require separately governed reanalysis/versioning.

`tests/database/test_api_review.py` seeds one fixture-only DRAFT case/candidate/artifact in `pulse_test` inside an outer transaction, exercises success, retry, stale, collision and unauthorized behavior, then rolls back everything. It never connects a write test to `pulse_dev`, repurposes legacy DRAFT, touches published snapshots, or creates production evidence. The design is deliberately fail-closed until a real identity/authority policy and new eligible workflow are approved.
