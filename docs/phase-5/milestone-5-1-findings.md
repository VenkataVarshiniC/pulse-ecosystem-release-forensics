## Decision, user and journey

The working persona is an engineer responsible for dependency upgrades or release-impact investigations across several owned repositories, often in platform/dependency-management work. The bounded product decision is: **Which declared repositories warrant further migration/remediation investigation after a significant dependency release, and what evidence supports that priority?** PULSE qualifies evidence and exposes uncertainty; it does not assign risk, prove causation, discover the ecosystem or automate organizational priority.

The [canonical workflow](m5-1/product-workflow.md) runs investigation list → selected release/case/snapshot → declared cohort → repository → grouped historical/source evidence → literal lifecycle findings → candidate and provenance inspection → conditional reasoned review → bounded finding or UNKNOWN → return to cohort. Branches may be skipped; categories are evidence classes, not mandatory chronology. A single proposed **investigator** role can inspect; only verified human reviewer capability can submit on eligible DRAFT evidence. This is a minimal capability distinction, not enterprise RBAC or a claim that reviewer identity is already validated. The current two published replay candidates, both inherited REJECT on one copied-upstream artifact, remain read-only.

## Product structure and behavior

The seven [specified screens](m5-1/screen-specification.md) are Investigation List, Investigation Overview, Repository Investigation, grouped Evidence Explorer, Finding Detail, Candidate Review, and Artifact/Provenance Detail. The list selects an exact release/case/snapshot without a score. Overview retains every declared cohort member and shows literal collection, historical, candidate and finding states. Repository detail separates declaration, actual resolved-version observation, historical pairing, source sufficiency and category findings. Evidence is grouped by source/category/ref; event time and retrieval time are separate and missing timestamps are explicit. Finding detail shows UNKNOWN, bounded NO or future qualifying evidence with reason, sufficiency, actual support and method version. Candidate detail separates tentative rule emission from a human decision, and inherited review from new human action. Artifact detail shows permitted source locator, capture method, ref/path, retrieval context and digest while withholding credentials and internal secrets.

Navigation keeps a case/snapshot breadcrumb through cohort → member → evidence/findings/candidates → provenance. State is multi-axis: snapshot publication, collection outcome, candidate emission, review decision/origin, sufficiency and finding are not collapsed into a fictional single lifecycle. No persisted CREATED/COLLECTED/ANALYZED case status is invented. Every screen has distinct no-data, loading, unavailable, scoped not-found, network/backend and unauthorized/invalid-action behavior as applicable. A failed read is never rendered as zero evidence.

The [uncertainty UX](m5-1/uncertainty-ux.md) keeps UNKNOWN, INSUFFICIENT, SOURCE_UNAVAILABLE, recorded CONFLICTING, bounded NO, no candidate, AFTER_ONLY, partial/unavailable metrics and 0/0 distinct. Missing evidence never visually becomes negative evidence. The current governed replay has **38 UNKNOWN, two bounded NO and zero positive findings**; it does not validate adoption/recovery across a population. A valid 0/N is limited to its exact eligible question, whereas 0/0 is unavailable. [Product copy](m5-1/product-terminology.md) preserves these governed meanings and avoids causal language.

## Requirements, contract and scope

The [requirements map](m5-1/requirements-to-product-traceability.md) covers all **28** Phase 3 formal requirements (**22 Must, six Should**) with priority, application capability, screen, API, acceptance anchor, existing status/gap and pending stakeholder status. The [six use cases](m5-1/use-case-reconciliation.md) are each classified: UC-01 partial, UC-02 directly supported as a product specification, UC-03 partial, UC-04 deferred, UC-05 partial (backend report generation exists; product reading specified), UC-06 partial for inspection with closure deferred. This does not claim implemented frontend or observed stakeholder use. [Future product acceptance checks](m5-1/product-acceptance-criteria.md) cover navigation, repository/evidence/provenance drill, literal findings, guarded review, no false zero, frozen evidence and empty/error states, referencing existing Phase 3 AC. They have not been executed as UAT.

The [API capability specification](m5-1/api-capability-spec.md) calls for bounded list/get investigation and cohort, repository detail, evidence/historical observations, artifact provenance, findings, candidates/reviews and a **conditional** candidate-review submission. The [screen/API matrix](m5-1/screen-api-matrix.md) ties each page to these capabilities and existing `core`, `ingestion` and optional governed read-only `analytics` data. Case/snapshot-scoped IDs, state, reason, version, method and provenance travel in typed responses. Operational reads and the current replay are read-only. The sole contemplated write is an atomic, reasoned human candidate review on an eligible new DRAFT target, after identity, authorization, stale/duplicate and V005 publication guards are satisfied; findings require separate governed reanalysis. Neither raw captures nor published snapshots can be edited from the frontend. An old DRAFT snapshot is not a substitute review target.

The strict MVP is list → overview → repository → evidence/provenance → finding → candidate/review **inspection**, with guarded review submission only when its prerequisites exist. It does not promise case creation, attention override or closure. The [out-of-scope register](m5-1/out-of-scope.md) excludes AI/RAG, ecosystem discovery, vulnerability scanning, update bots, CI/CD, predictive scoring, billing, enterprise RBAC, notifications, production multi-tenancy, cloud deployment, mobile, new evidence methods and Power BI implementation.

The planned application layer is **React + TypeScript → FastAPI/Python → PostgreSQL → existing PULSE evidence and analysis**. React/TypeScript suffice for seven bounded, typed, navigable screens; FastAPI/Python naturally sits with the existing Python validation/evidence methods and PostgreSQL without redesigning them. Neither framework is implemented here. The application handles operational repository investigation and potential human review. The [frozen, deferred Power BI handoff](../phase-4/m4-2/power-bi-build-handoff.md) handles later aggregate analytical decision support: compare patterns, visualize governed metrics and summarize cohorts. It does not navigate original artifacts or submit reviews; the frontend is not a duplicate dashboard.
