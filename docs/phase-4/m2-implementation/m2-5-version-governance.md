# M2.5 versions and publication gate

`analytics/metrics/metric_registry.yml` is the technical contract `m2-5-metric-registry-v1`: exactly 23 names, statuses, populations, numerators, denominators, null rules, and dependencies. Its SHA-256 is recorded in `data/manifests/analytics-release-manifest.json`. This version does **not** mean stakeholder approval. The mart model is `m2-4-831121996a8f-c98464051fc0`: the M2.4 source commit `831121996a8fb674bee3a0bd4aeeb0e5dfb428b7` plus SHA-256 of dbt models, macros, and project contract. dbt Core is pinned at 1.11.15 and the isolated PostgreSQL cluster is major 16. The manifest binds these to generated metric/diagnostic hashes, the Phase 2 load-manifest file hash, and both source snapshot manifest hashes.

The **frozen rule version remains unresolved**. The M2.2 loader explicitly writes `RULE_VERSION = "unrecorded_in_frozen_report"` into case/snapshot/finding provenance and `unrecorded_in_frozen_baseline` for candidates. The frozen Phase 2 report/baseline does not identify the exact detector configuration and source revision that produced each selected result. Current repository rule code or a later commit cannot safely be retroactively asserted as the executed rule. A candidate-rule ID is not a version. The release manifest therefore records an unresolved version rather than inventing one.

Both source snapshots have `state=DRAFT`, `metric_definition_version=not_yet_modeled`, and `model_version=postgres-core-v4`. M2.5's technical contract/model versions govern **this validation output**, not those earlier source rows. A valid publication would require a new immutable canonical manifest and snapshot identity with all rule, metric, model and input versions traceable, plus explicit approval and revalidation. Direct row edits and silent dbt replacement of a published historical output are forbidden by the M2-PREP snapshot contract. M2.5 creates no publication state transition: previous DRAFT → current DRAFT for both snapshots, with no publication time. The validation manifest's generation time is not a publication time.

`PUBLISHED` would mean a bounded frozen, reproducible analytical snapshot approved for consumption under its stated scope. It would **not** mean stakeholder validation, ecosystem representativeness, proven adoption or recovery, or product-market fit. Here the publication gate is `HOLD_DRAFT`; BI is `BLOCKED_NO_PUBLISHED_SNAPSHOT`. Even if the semantic relationships and metric contract are technically valid, Power BI cannot consume these DRAFT snapshots under the governed gate. Source fingerprints and rerun checks preserve this hold without adding a warehouse-versioning mechanism that is not yet needed.
