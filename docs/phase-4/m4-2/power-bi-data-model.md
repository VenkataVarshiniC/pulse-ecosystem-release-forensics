## Snapshot selector and relationships

In M4.2 derive a one-row-per-approved-snapshot `SnapshotScope` selector from **distinct published** `(analysis_snapshot_id, case_key, snapshot_state, source_metric_definition_version, mart_model_version)` in `bridge_case_repository`, cross-checked against the manifest's two exact IDs. Exclude all DRAFT rows *before* loading/reporting, not merely with a removable visual filter. Use a single-select case/release slicer followed by a single-select snapshot; measures must return blank/“Select one published case and snapshot” unless `HASONEVALUE(analysis_snapshot_id)` and the case matches. Keep snapshot ID in a provenance panel and drill-through even though it is hidden from headline visuals. Default only to `PUBLISHED_VALIDATION`. Do not silently combine pytest and urllib3 into a rate; any explicit two-case comparison must compute case-level rates first with each case's own eligible denominator and label the population.

The conceptual membership path is `dim_case → bridge_case_repository ← dim_repository`, with `dim_release → dim_case`. The actual one-way Power BI cardinalities are release 1:m case, case 1:m bridge, and repository 1:m bridge; a case filter must not be expected to propagate *backwards* through the bridge to `dim_repository`. Use the bridge's member rows for a case-filtered repository slicer, or a controlled `SnapshotScope × member` semantic table. `SnapshotScope` is 1:m to both bridge and `fct_collection_task`, filtering one way by `analysis_snapshot_id`. For member-scoped facts, create a stable composite semantic key from `(analysis_snapshot_id, case_key, repository_key)` in Power Query, with `bridge_case_repository` 1:m to each of `fct_repository_investigation`, `fct_candidate_review`, `fct_lifecycle_finding`, and `fct_evidence_observation`; use one-way bridge-to-fact filtering. `fct_repository_investigation` is effectively 1:1 on this key. Preserve the component keys in data for audit. Direct `dim_evidence_source.source_key` 1:m single-direction joins are permitted to task, candidate, and observation facts; `dim_release` reaches selected facts only through case/scope. If a tool cannot enforce the composite member key without ambiguity, use explicit case/snapshot filtering in isolated fact measures rather than a many-to-many shortcut.

The shared upstream task's NULL repository key makes a bridge-only task path unsafe. Keep its independent `SnapshotScope → fct_collection_task` route. Do not add competing direct case-to-member-fact routes that make an ambiguous filter graph. Do **not** join two facts directly on repository, artifact, or case; do not enable global bidirectional relationships. `bridge_finding_evidence` is a drill-through-only child of a selected `(snapshot_id,finding_id)` and must not be on a counting or denominator path. Validate the exact cardinalities and absence of fanout before visual construction.

## Metric and provenance boundary

The unchanged contract is `m2-5-metric-registry-v1`, defined in `analytics/metrics/metric_registry.yml` and executed by `analytics/sql/metrics/*.sql`; the [published replay output](../../../data/validation/m4-1b-replay-metrics.json) has 23 results per snapshot. **SQL/dbt owns eligibility, missingness, status, numerator, denominator, and evidence sufficiency.** Future DAX may aggregate in the selected scope, format, label, and use `DIVIDE` to preserve a blank result for a zero denominator. It must not redefine a governed metric, infer status from a blank alone, recode UNKNOWN to NO, or create a rate from PARTIAL components. The table below is a display specification, **PROPOSED — NOT YET IMPLEMENTED** in Power BI.

| Display measure / contract | Authoritative mart or output; N / D | Unavailable and display rule |
|---|---|---|
| Core Collection Coverage / MET-001 | `fct_repository_investigation` plus member bridge; members with required core collection complete / declared members | Show N/D and percentage only when READY; invalid plan or missing denominator → “Unavailable” with reason. |
| Historical Context Coverage / MET-002 | Member/observation fact; members with qualifying exact-ref declaration / declared members | Show N/D; label **declaration coverage**, not adoption or paired-history rate. |
| Candidate Emission Coverage / MET-008 | Member bridge plus candidate/member fact; members with ≥1 candidate / declared members | Show N/D; `0/2 = 0%` is a valid zero *emission*, not zero friction. |
| Reviewed Candidate Acceptance / MET-009 | Candidate fact; accepted selected IDs / terminally reviewed ACCEPT-or-REJECT IDs | `0/0 → Unavailable`, never `0%`; urllib3 `0/2 → 0%` is valid. Show inherited-review label. |
| UNKNOWN finding composition / MET-012 | Finding fact; UNKNOWN reported findings / reported selected findings | Registry status is PARTIAL_EVIDENCE: show counts and a clearly descriptive composition only; **withhold a governed “UNKNOWN Rate” KPI** until question-set eligibility is approved. |
| Required Task Completion / MET-016 | Task fact; succeeded required tasks / all planned required tasks | Show N/D and percentage only for a verified selected plan; optional failures stay separate. |

Other READY, PARTIAL, unavailable, and stakeholder-blocked contracts retain their v1 statuses; consult the result JSON for each case. Adoption/recovery and MET-006 completion remain unavailable/blocked, so there is no corresponding KPI. `0/0` is unavailable; zero numerator with a valid denominator is a valid numeric zero. UNKNOWN is a visible finding state. `INSUFFICIENT` is an evidence prerequisite state, not evidence of absence. `NO_QUALIFYING_EVIDENCE_FOUND` is a bounded NO only under its selected sufficient assessment. `REJECT` is a review disposition, not absence of migration friction. No candidate emitted is separate from a rejected candidate and from an UNKNOWN finding.

The replay `candidate_rule_version` and finding `rule_version` are in marts, but the full replay release/rule-manifest hash must come from the publication manifest, **not** `dim_case.rule_version` (the original case-definition field). `fct_candidate_review` currently lacks inherited-review origin, original review UUID, exact-equivalence basis, and artifact locator; `bridge_finding_evidence` has zero rows.
