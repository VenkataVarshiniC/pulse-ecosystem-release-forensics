## Reliable project description

PULSE is a repository-bounded dependency-release investigation prototype. It collects declared public GitHub/PyPI sources, preserves provenance, reconstructs partial exact-ref dependency context, generates rule-based candidates for human review, and presents versioned findings through reports, PostgreSQL/dbt analytics, Power BI, and a React/FastAPI interface. Its strongest evidence is auditability and explicit uncertainty. Its automated validation cases do not establish reliable adoption, compatibility, recovery or causal release impact.

## Results and limits

Published two-case baseline: 8 members; 40 findings = 38 UNKNOWN, 2 bounded NO, 0 positive; 2 rule firings from one shared Dependabot artifact, both rejected. The exact package/version plus keyword rules are candidate generators, not validated incident classifiers. No recall denominator exists; 0/2 accepted among reviewed emissions is not population precision. The earlier HTTPX accepted examples are a different, connector-assisted demonstration.

Phase 7 committed evaluation: paired historical path records 1→5 out of 16; sufficient assessments 2→6 out of 40; UNKNOWN 38→34; bounded NO 2→6; positives and support links remain zero. All 48 bounded attempts have recorded complete provenance. These are method-coverage improvements, not improved adoption/recovery detection or user outcomes. Synthetic test fixtures produce different numbers and must not be quoted as live experimental results.

Collection code implements token authentication, pagination/deduplication, bounded retries/rate-limit handling, explicit failure outcomes, exclusive-create journals and digest/identity verification before resume. It does not establish exhaustive evidence discovery or representative downstream selection. History uses path-scoped anchors; declaration evidence does not prove installation or runtime compatibility. Missing evidence is UNKNOWN; bounded NO means no qualifying evidence within sufficient declared sources, not proof that no event occurred.

## Tests and reproducibility

- Independently observed GitHub Actions execution: main CI run 36258206360, quality job 108448901320; Ruff passed and pytest logged 40 passed.
- Later recorded execution: Phase 7 closure reports 204/204 Python tests (10 focused Phase 7 tests); M5.4 reports 11 frontend tests, typecheck/lint/build; publication manifest records 30 dbt models and 173 test passes. Source/test artifacts exist, but these later execution counts were not independently rerun or corroborated by later Actions runs. Actions listed only two runs.
- Replay safeguards are implemented and tested: case/task/source hashes, candidate/review identity, deterministic output, drift rejection, and isolated method versions. M4.1B records 46 metric outputs rerun byte-identically.
- Critical portability limit: Phase 2 baseline manifests point to external Windows capture roots; the load manifest identifies four external roots. Full replay/database loading is not self-contained in a fresh clone. Recorded hashes and summaries are not a substitute for possessing and verifying those original bytes.
- Power BI validation is recorded manual/Desktop/DAX execution with committed PBIP/PBIR/TMDL, not a session rerun during this audit.

## Claims to avoid

Do not claim ecosystem-wide monitoring, unbiased adoption/friction rates, exhaustive impact discovery, validated detector accuracy/recall, installed adoption, compatibility/recovery measurement, causal attribution, production scalability, proven time savings/ROI, or stakeholder acceptance. Survey interest and technical QA do not prove workflow value. “204 CI tests passed” and “fully reproducible from a clone” overstate available evidence. “Only Phase 2 exists” understates the branch implementation.
